① The Scope  — what are we building?

read this first ↓

A local-first push-to-talk → cleaned text tool that goes one step further than Superwhisper: a small open-source LLM reads the tail of every transcript looking for format intents ("…format as markdown", "…make a checklist"), then formats and/or routes the output via tools (clipboard, file, calendar, etc). Two transcript engines run side-by-side so we can A/B Whisper variants vs Apple's on-device model.

A System architecture (one diagram)

Three lanes — capture, brains, output — with two pluggable "engine racks" on either side.
whispr_arch.sketch
capture two ways in: mic hotkey OR a file drop. Audio → bytes → engine rack.
brains cleanup → command-sniffing → formatter or tool call. All driven by a single, small local model.
output one paste-at-cursor by default, but the agent can also fan out to files, notes apps, calendars, GitHub…

④ Format Commands  — "…format as markdown"

how does the model know what you want?

The trailing-command pattern is the heart of the project. Two questions: how do we detect it (regex? LLM? both?) and how do we surface it (chip? sidebar? inline tag?).

● Vocabulary

Starter set of commands the parser will recognize.
format as markdown → .md
make a list / bullet points → - item
checklist / todo → [ ] item
numbered / steps → 1. step
as a table → | a | b |
draft an email to X → email block
add to my calendar → tool call
save as <name>.md → tool: write_file
commit it / ship it → just run it
just clean it up (default)

● Parser pipeline

Hybrid: cheap path first, LLM fallback.
raw transcript: "… milk, eggs, bread, make a checklist"
↓
step 1 · regex / phrase~10 patterns, instant
hit? → done→format:checklist (conf 1.0)
↓
step 2 · LLM classifier~150 tokens, ~200ms
"give me this as 3 sections"→format:markdown_sections
low confidence → bubble a "Did you mean…" chip in the preview.

● Where the command "lives"

In the prompt to the LLM, we split content from intent.
## SYSTEM You receive a noisy transcript that may end with a format command. Split into: <content>...</content> <intent>clean | list | check | steps | table | email | markdown | tool:<name></intent> Then format <content> per <intent>. ## USER "milk eggs bread make a checklist" ## EXPECTED <content>milk, eggs, bread</content> <intent>check</intent> - [ ] milk - [ ] eggs - [ ] bread

⑥ Agent + Tools  — "save as today.md" → it just does it

how does tool calling feel?

Once the LLM can act, the trailing command stops being just "format" and starts being "do this with this." Big trust questions hang on this: does the user confirm tool calls, or do they trust-and-fire? How do we visualize what the agent did?

● Tool registry (v1)

  • clipboard.copy — default; no permission needed
  • file.write — to a configured "inbox" folder
  • obsidian.append — to a daily-note in a chosen vault
  • calendar.create_event — EventKit on macOS
  • reminders.create — Reminders.app
  • github.create_issue — repo whitelist
  • shell.run — opt-in, allowlisted commands only
  • web.search — DuckDuckGo / Brave

● Permission model — user-configurable

Sensible defaults below; every tool has a permission level the user can flip in Studio › Settings › Tools.
tool auto ask off
clipboard.copy●○○
format → markdown / list / check●○○
file.write → inbox folder●○○
file.write → anywhere else○●○
obsidian.append (daily note)●○○
calendar.create_event○●○
github.create_issue (later)○●○
shell.run (later)○●○
web.search (later)○○●
auto = just run, no prompt. ask = inline confirm with "remember this choice" toggle. off = tool not callable. Rule of thumb: formatting + clipboard + writes to an opted-in folder are auto; anything that creates state in another app or runs code asks first.

● Single vs multi-agent

v1 — single agent, LangChain function-calling. 99% of cases.
v2 — multi-agent toggle (CrewAI): {transcriber} → {cleaner} → {formatter} → {router}. Mostly for the writeup / "look it can do this too."
